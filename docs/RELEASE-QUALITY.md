# خط کنترل کیفیت انتشار و بازگشت نسخه

## خروجی این مرحله

Workflow `Release quality` در `.github/workflows/quality.yml` روی PR، پوش به `main` و اجرای دستی فعال می‌شود. با دسترسی فقط‌خواندنی مخزن و بدون اسرار محیط تولید، این موارد را اجرا می‌کند:

1. TypeScript، تست‌های واحد/رگرسیون، ممیزی وابستگی‌ها و ساخت تمیز خروجی کامپایل‌شده.
2. دو دیتابیس جدا و خالی PostgreSQL 16 برای تست یکپارچه قدیمی و تست امنیتی جدید.
3. Playwright واقعی روی Chromium در اندازه دسکتاپ و موبایل: ورود، ثبت پرونده با مراحل فرم، ثبت پیگیری، بررسی/تأیید/ارجاع مالی و پرداخت با حساب جداگانه مالی. ورود و دامنه داده ۱۲ نقش ساختگی هم بررسی می‌شود. APIها شبیه‌سازی نمی‌شوند؛ فقط داده اولیه تست ساخته می‌شود.
4. تمرین بکاپ رمزگذاری‌شده، بازیابی، اعتبارسنجی داده و سازگاری اجرای کد کامیت قبلی با دیتابیس بازیابی‌شده.
5. ساخت Docker production و اعتبارسنجی پیکربندی Compose.

`Release gate` فقط وقتی موفق است که **همه** jobها موفق باشند؛ لغوشدن یا skipped شدن هم موفق محسوب نمی‌شود. بسته `verified-release-<commit>` تنها بعد از این دروازه، برای پوش موفق `main` تولید می‌شود و SHA کامیت و checksum دارد. این workflow دیپلوی خودکار یا GitHub Release ایجاد نمی‌کند.

**مهم:** وجود CI به‌تنهایی جلوی پوش مستقیم یا دیپلوی یک سرویس خارجی از `main` را نمی‌گیرد. برای تحقق الزام «نسخه ناموفق وارد انتشار نشود»، مدیر مخزن باید:

- در Settings → Rules → Rulesets، شاخه `main` را مشمول قانون فعال کند.
- PR قبل از مرج و status check به نام **Release gate** را اجباری کند؛ ترجیحاً به‌روز بودن شاخه و منع bypass را هم فعال کند.
- دسترسی GitHub Actions را فعال نگه دارد و بعد از اولین اجرا همان check را انتخاب کند.
- هر CD یا سرویس میزبانی متصل به مخزن را به بسته تأییدشده و موفقیت همین دروازه وابسته کند، نه صرفاً رخداد push.

اعمال قواعد مدیریتی مخزن و استقرار سرور جزو تغییر فایل‌های این کامیت نیست. موفقیت محلی نیز جای نتیجه اجرای GitHub Actions را نمی‌گیرد.

## ساخت و اجرای نسخه کامپایل‌شده

```sh
npm ci
npm run verify
# اتصال دیتابیس همان محیط باید از قبل تنظیم شود
npm run migrate:compiled
npm run start:compiled
```

`verify` کنترل‌های بدون دیتابیس را اجرا می‌کند: تایپ‌چک، تست واحد، ممیزی و build. تست یکپارچه، مرورگر و بازیابی jobهای جداگانه CI هستند. `build` خروجی `dist` را از نو می‌سازد و فایل CommonJS قوانین گزارش را که TypeScript تولید نمی‌کند نیز کپی می‌کند. Docker دو مرحله‌ای، runtime کامپایل‌شده بدون وابستگی‌های توسعه دارد؛ سرویس migrate در Compose production از `migrate:compiled` استفاده می‌کند. فرمان‌های توسعه `dev` و `migrate` با tsx برای سازگاری باقی مانده‌اند.

## محیط staging با داده ساختگی

هیچ داده یا پشتیبان واقعی را وارد محیط QA نکنید. محیط Docker مجزا:

```sh
docker compose -p charity-qa -f docker-compose.qa.yml up --build
```

فقط `http://127.0.0.1:4180` منتشر می‌شود. شبکه و volume این پروژه باید از production جدا بماند. حساب‌های `qa_admin`، `qa_liaison`، `qa_health_officer`، `qa_education_officer`، `qa_supervision_deputy`، `qa_finance_officer` و سایر نقش‌های QA رمز عمومی و **صرفاً ساختگی** `SyntheticQaPass123` دارند. این محیط نباید عمومی یا حاوی اطلاعات واقعی باشد. `seed:test` روی دیتابیس دارای جدول کاربران اجرا نمی‌شود و داده موجود را پاک نمی‌کند. برای ساخت دوباره QA، فقط همان پروژه QA را با `docker compose -p charity-qa -f docker-compose.qa.yml down -v` پاک و دوباره ایجاد کنید؛ هرگز این دستور را روی پروژه تولید اجرا نکنید.

اجرای محلی بدون Docker، برای هر فرمان یک دیتابیس **جدید، خالی و دورریختنی** لازم دارد:

```sh
TEST_DATABASE_URL=postgresql://qa:...@127.0.0.1:5432/charity_legacy_test npm run test:integration
TEST_DATABASE_URL=postgresql://qa:...@127.0.0.1:5432/charity_security_test npm run test:security:integration
npx --no-install playwright install chromium
TEST_DATABASE_URL=postgresql://qa:...@127.0.0.1:5432/charity_browser_test npm run test:browser
```

نام، رمز و پورت باید متعلق به کاربر PostgreSQL آزمایشی خودتان باشد. برای تست مرورگر/seed/recovery، میزبان فقط loopback و نام دیتابیس با پسوند `_test` مجاز است. Playwright reuse سرور قبلی ندارد و retries خاموش است. فایل‌های فیکسچر، گزارش مرورگر و بکاپ‌ها در گیت ثبت نمی‌شوند؛ گزارش شکست CI فقط داده ساختگی دارد و سه روز نگهداری می‌شود.

## تمرین بازیابی و بازگشت کد

نیازمند `pg_dump` و `pg_restore` نسخه 16 و اجازه ایجاد دیتابیس برای کاربر **آزمایشی** است. این سطح دسترسی را برای اجرای عادی برنامه لازم ندانید.

```sh
npm run build
# فقط یک بار در workspace تمیز؛ ref باید نسخه قبلی مشخص باشد
node scripts/prepare-rollback.mjs HEAD^
TEST_DATABASE_URL=postgresql://qa:...@127.0.0.1:5432/charity_recovery_test \
ROLLBACK_APP_DIR="$PWD/.tmp/rollback-release" npm run test:recovery
```

تمرین، داده ساختگی تولید می‌کند، با کلید تصادفی AES-256-GCM بکاپ می‌گیرد و به دیتابیس آزمایشی جدا بازمی‌گرداند. کلید غلط، خرابی tag و نبود تأیید مقصد باید **قبل از تغییر مقصد** شکست بخورند؛ بازنویسی فایل بکاپ موجود هم ممنوع است. تعداد و هش محتوای همه جدول‌های عمومی مقایسه می‌شود؛ مهاجرت دوباره اجرا و تغییرنکردن منبع کنترل می‌شود. برنامه کامپایل‌شده باید بعد از بازیابی آماده شود، ورود را بپذیرد و پرونده را بخواند. با `ROLLBACK_APP_DIR`، همین smoke test روی کد قبلی و سپس دوباره کد جدید انجام می‌شود. مقصد موقت و کلید/بکاپ تمرین در پایان پاک می‌شوند؛ دیتابیس منبع ساختگی برای بررسی باقی می‌ماند.

CI کامیت قبلی را از تاریخچه دوکامیتی می‌سازد. این **آزمون سازگاری محدود کد قبلی** است، نه اثبات سازگاری همه عملیات یا جایگزین آخرین image موفق production. مدیر انتشار باید digest/image یا بسته آخرین نسخه سالم و SHA آن را مستقل نگه دارد.

## بکاپ و بازیابی عملیاتی

فرمت رمزگذاری‌شده `FCBK1` قبلی حفظ شده است. حالت پیش‌فرض ابزارها Docker Compose است؛ برای production متغیر `COMPOSE_FILE=docker-compose.production.yml` و نام پروژه صحیح را تنظیم کنید. حالت `BACKUP_TRANSPORT=local` از `DATABASE_URL` و ابزارهای PostgreSQL محلی استفاده می‌کند؛ رمز اتصال در آرگومان فرایند قرار نمی‌گیرد. کلید را از secret store یا محیط امن تزریق کنید، نه متن کامیت یا تاریخچه shell.

```sh
# BACKUP_ENCRYPTION_KEY باید از محیط امن تأمین شده باشد
npm run db:backup -- /secure-backups/pre-release.dump.enc
# فقط پس از توقف نوشتن و تأیید مقصد؛ این فرمان داده مقصد را جایگزین می‌کند
RESTORE_DATABASE=family_case_restore RESTORE_CONFIRM=family_case_restore \
npm run db:restore -- /secure-backups/pre-release.dump.enc
```

ابزار restore برای **هر** مقصد تأیید دقیق نام را می‌خواهد؛ مقصد باید از قبل ساخته شده باشد. کل بکاپ ابتدا احراز اصالت می‌شود، سپس `pg_restore --single-transaction --exit-on-error` اجرا می‌شود. فایل رمزگشایی موقت در پوشه خصوصی ۷۰۰ و فایل ۶۰۰ نگهداری و در پایان حذف می‌شود؛ فضای کافی و دیسک امن برای temporary storage لازم است. خاموشی ناگهانی می‌تواند فایل موقت باقی بگذارد؛ سیاست پاک‌سازی امن میزبان لازم است. بکاپ باید از منبع مورد اعتماد باشد و مجوز نقش‌های دیتابیس، اسرار، TLS و فایل‌های خارج از DB جداگانه مدیریت شوند؛ dump با `--no-owner --no-acl` مالکیت‌ها و ACL تولید را بازسازی نمی‌کند.

## Runbook انتشار/rollback

1. آخرین بسته موفق، SHA و checksum آن را نگه دارید. موفقیت `Release gate` همان SHA را کنترل کنید.
2. در پنجره نگهداری نوشتن را متوقف کنید، بکاپ پیش از انتشار بگیرید و بازیابی آن را در مقصد جدا آزمایش کنید. زمان/RPO/RTO متناسب با داده واقعی باید اندازه‌گیری شود؛ این تست مصنوعی عدد عملیاتی تضمین نمی‌کند.
3. مهاجرت و استقرار candidate تأییدشده را انجام دهید؛ readiness، ورود، پرونده، پیگیری، تأیید و پرداخت مجاز را smoke کنید.
4. در مشکل صرفاً کد و سازگاری schema، با نوشتن متوقف به **همان artifact/image سالم قبلی** برگردید؛ کد را از شاخه متحرک بازسازی نکنید و مهاجرت را کورکورانه معکوس نکنید.
5. اگر schema ناسازگار یا داده آسیب دیده است، بازگشت دیتابیس فقط با تأیید مسئول داده و برنامه رسیدگی به تراکنش‌های پس از بکاپ انجام شود. ترجیحاً در مقصد جدا restore و سپس اتصال را جابه‌جا کنید؛ restore می‌تواند داده‌های بعد از زمان بکاپ را از بین ببرد.
6. بعد از کنترل لاگ و smoke، نوشتن را باز کنید. هیچ‌کدام از این عملیات تولید با push کردن این کامیت خودکار انجام نمی‌شود.
