# ساختار بک‌اند و قراردادهای مشترک

## مرزهای فعلی

- `domain/familyInput.ts`: اعتبارسنجی مشترک ثبت، ویرایش، ورود اطلاعات و تأیید خانواده؛ مسیر قدیمی export برای سازگاری نگه داشته شده است.
- `domain/financial.ts`: فهرست وضعیت‌ها و قواعد انتقال مالی؛ `domain/approval.ts`: ورودی تصمیم و allowlist فیلدهای قابل تأیید.
- `services/familyPolicy.ts`: محدوده خانواده و بایگانی برای guard مشترک. این لایه جایگزین مجوز اختصاصی عملیات و واحد تخصصی نیست.
- `services/financial.ts`: انتقال مالی و پرداخت، داخل تراکنش. هندلر HTTP همچنان ورودی، فایل و پاسخ را مدیریت می‌کند.
- `services/approvals.ts`: تصمیم‌گیری درباره خانواده جدید و تغییرات آن؛ خواندن وضعیت، اعمال تغییر، تصمیم و audit همگی در یک تراکنش و با قفل ردیف انجام می‌شوند.
- `repositories/financial.ts`: قفل پرونده مالی و قفل مشترک صندوق/دوره. تغییر بودجه و پرداخت از یک کلید قفل استفاده می‌کنند؛ صندوق فعال هنگام پرداخت قفل اشتراکی می‌گیرد.
- `audit.ts`: قرارداد مشترک رویدادهای audit؛ نام و محتوای رویدادهای قبلی حفظ شده‌اند.
- `domain/errors.ts`: خطای دامنه با کد عمومی ثابت. خطاهای هم‌زمانی PostgreSQL به `409 RETRYABLE_CONFLICT` تبدیل می‌شوند، بدون تلاش مجدد خودکار برای عملیات غیر idempotent. پاسخ‌ها `x-request-id` دارند.

## تضمین‌ها و محدودیت‌ها

قفل پرونده مالی، کلید idempotency پرداخت و محدودیت‌های بانک اطلاعاتی حفظ شده‌اند. رقابت دو تأیید فقط یک تصمیم موفق و یک audit می‌سازد؛ درخواست دوم وضعیت جدید را می‌خواند و 409 می‌گیرد. guardهای پایگاه داده گام اول همچنان آخرین خط دفاع در برابر نوشتن روی بایگانی‌اند.

این بازآرایی تدریجی است: SQL همه ماژول‌ها منتقل نشده و مسیرهای قدیمیِ سالم بی‌جهت بازنویسی نشده‌اند. جداسازی بیشتر مسیرهای عملیات، تخصصی و گزارش‌ها باید همراه تست همان قابلیت انجام شود. تغییری در schema یا داده‌های واقعی لازم نیست.

## آزمون

`npm run verify` به‌اضافه `test:integration` و `test:security:integration` روی دیتابیس‌های خالی و دورریختنی. تست‌های رقابت تأیید خانواده، تأیید اصلاح، انتقال مالی، پرداخت تکراری و بودجه مشترک در مجموعه integration هستند. تست مرورگر دسکتاپ و موبایل نیز پیش از تحویل اجرا شود.
